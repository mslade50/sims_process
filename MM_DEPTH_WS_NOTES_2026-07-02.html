Semantics worth remembering

  • Yes-taker ladder: Kalshi's orderbook arrays are resting bids per side. A YES taker crosses the NO bids, so the YES ask ladder is 100 − each NO bid. Depth = $ stake available within 1¢ of best ask (_yes_taker_depth, board/build.py).
  • Fallback chain (fail-soft, never blocks a build): exact orderbook depth → liquidity/4 proxy (whole book, both sides, so a quarter is conservative) → uncapped. Non-exchange books (Betcris/BOL/Pinnacle — no depth concept to scrape) are uncapped, i.e. status quo.
  • Caps are enforced client-side, because dollars need a bankroll and only the browser knows it. Both solve paths clamp each bet's stake at its chosen book's depth. Browser re-solve clamps before the P&L loop (risk summary stays exact); the server fast path clamps after κ-scaling, so its aggregate ret_dist slightly overstates exposure for capped bets — the UI notes this whenever caps bit.
  • Depth is a snapshot. It's stale the moment it's fetched. A cap means "never plan to take more than was visible," not a fill guarantee — same philosophy as the maker's re-fetch-before-POST invariant.
  • Refinement not done (deliberately): the clamp is post-solve, not a box constraint inside the optimizer — clamped-off stake isn't redistributed to other bets. It's strictly conservative. If caps bind often, add upper bounds to pfOptimize/solve_kelly's projection (clamp-within-projection is a small change; the server side would also need an assumed bankroll, which is why it wasn't done now).

2 · The WebSocket path (deferred, on purpose)

Kalshi's WS API has an orderbook_delta channel: one authenticated connection, any number of tickers, an orderbook_snapshot per subscription then sequenced deltas. It is the correct transport for a standing consumer that needs current book state continuously. We deferred it because neither consumer is a standing process — by design:

  • The board is a batch CI job: it would connect, wait for snapshots, disconnect — a REST snapshot with extra failure modes. The stream part would go unconsumed. The board stays batch forever.
  • The maker is a systemd oneshot + 2-min timer + rolling native TTL. Its load-bearing safety property is the process dying is always safe (crash / kill -9 / reboot → quotes self-cancel ≤600s). A WS consumer means a long-running daemon whose death or silent book-state drift is the dangerous state — an inversion of the risk model the whole 07-01 audit was built around.
  • Rate limits are a non-problem: total need is a few hundred reads/day against 10/sec. WS solves a limit we don't hit, at the price of an ops burden we don't carry.

What survives a WS future (why Tier 0/1 isn't throwaway)

The durable layer — ticker/liquidity on scraped lines, per-bet depth schema, the clamp/box-constraint plumbing, the fallback chain — is transport-agnostic. A WS book store changes where the depth number comes from: one function swaps a REST call for a D1/file read. The expensive parts of a standing engine (sequence-gap handling, reconnect semantics, supervision, state reconciliation) share almost no code with the snapshot path in either direction.

Step 1 if/when: the read-only book recorder

The right first brick is NOT converting the maker — it's a standalone recorder: a WS consumer (VPS process or a kalshi_exec Durable Object) that maintains book state for the golf series and writes snapshots to D1/parquet, touching no orders. Maker and board read it when fresh, fall back to REST when not. It solves the hard book-state problems on zero-risk infrastructure, leaves the oneshot safety model untouched, and its data directly answers whether an event-driven maker is even worth building.
  • Auth: WS connect uses the same RSA key signature as REST (kalshi_auth already builds these headers).
  • State discipline: per-ticker sequence numbers; any gap → drop book, resubscribe for a fresh snapshot. Never patch over a gap.
  • Staleness stamp: every written snapshot carries as_of; consumers gate on it exactly like sim_run_at — unstamped or old ⇒ fall back to REST. Same fail-closed pattern as everything else in this system.
  • Ops: it's a standing process — systemd service (not oneshot) with restart, healthchecks ping, Telegram on death. Budget for it paging you.

Step 2 (much later): the event-driven maker

Re-quote when the book moves instead of on the 2-min clock; track queue position; size off live depth every cycle. This is a rewrite of the maker's process and risk model — supervision, heartbeats, reconciliation-on-restart — and should be A/B'd against the known-good oneshot at small caps, never swapped in wholesale.

Decision gates — build the recorder when live data shows any of:

SignalWhat it means
Fills consistently worse than the quoted price's queue implied Queue position matters → need book state, not snapshots
Quotes routinely re-quoted past / picked off between 2-min cycles Golf books move faster than the cadence → event-driven re-quote pays
Depth caps binding on most candidate bets at your actual caps Sizing needs finer, fresher depth than build-time snapshots
Raising maker caps past small-ball The economics start covering a standing process's ops cost

Until one of those shows up in the supervised-live / early-live fill data, the snapshot path is not a compromise — it's the right architecture for batch consumers.
